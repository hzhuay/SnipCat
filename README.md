# SnipCat

按时间段无损切分视频并拼接的桌面工具。给一个视频、几个时间段，切出来拼成一个文件，编码参数与原视频完全一致。

**核心特点是它不骗你**：流复制只能在关键帧上切，实际切点必然与你输入的时间有偏差。界面会把每一段的真实切点和多切量标出来，而不是静默地切歪。

## 为什么做这个

这是一个高频且边界完全确定的流程：看视频记下几个时间段，切出来拼一起。没有任何需要推理的地方，用 AI 对话或命令行都是杀鸡用牛刀 —— 每次要开对话、拼参数、等结果。做成图形界面后是零延迟的确定性操作。

## 功能

- 拖入视频或点选文件，自动读取编码参数
- 时间段列表：宽松的时间输入（`13` / `1:30` / `00:00:13` / `1:02:03.5` 都认）、拖拽排序、实时校验
- 内置播放器边看边打点，时间轴上可直接拖动段落的起点/终点
- 显示每段的真实切点与多切量，偏移可见而非静默发生
- 输出到原视频同目录，文件名加可编辑的后缀，容器格式保持一致
- 多音轨、内封字幕全部保留
- 进度条、取消、完成后在文件管理器中定位
- Dry-run 模式：只输出 ffmpeg 命令不执行，方便核对或手动跑

## 快捷键

| 键 | 作用 |
|---|---|
| `←` / `→` | 后退 / 前进 3 秒（按住 `Shift` 为 10 秒） |
| `空格` | 播放 / 暂停 |
| `回车` | 智能打点：先设起点，再按设终点 |

回车的判定：存在只有起点的段落时补终点（当前位置必须在该起点之后，否则提示无效且不改动数据）；所有段落都完整时开始标新的一段。

## 环境要求

需要系统里有 **ffmpeg 和 ffprobe**（应用不内置，从 PATH 取）。

- Windows：`winget install Gyan.FFmpeg`，或从 [gyan.dev](https://www.gyan.dev/ffmpeg/builds/) 下载后把 `bin` 目录加入 PATH
- macOS：`brew install ffmpeg`

建议 ffmpeg 6.0 以上。开发需要 Node 22+。

## 使用

```bash
npm install
npm run dev          # 开发模式，改代码热更新
npm run build:win    # 打 Windows 包（portable exe + NSIS 安装包）到 release/
```

## 两种切分模式

| | 流复制（默认） | 精确切分 |
|---|---|---|
| 画质 | 无损，原始码流逐帧不变 | 一次重编码损失 |
| 切点 | 吸附到关键帧，两端向外扩 | 帧级精确 |
| 耗时 | 几秒 | 长视频以分钟计 |

**切点偏移是编码原理决定的物理限制，不是实现缺陷。** P/B 帧依赖前面的关键帧，不重编码就无法从任意帧开始。

吸附方向是**两端都向外**：起点向前吸附到关键帧，终点向后吸附到帧边界。宁可多切几帧，也不缺内容。界面上标的是「多切 头 +0.37s / 尾 +0.02s」，因为多出来的部分确实是多出来的，而不是丢掉的。

精确模式用 ffprobe 读到的参数重建编码器设置（codec / profile / level / pix_fmt / 分数帧率 / bitrate / 色彩元数据），视觉上与原视频一致但不是原始码流。遇到没有对应编码器的 codec（如 ProRes）会禁用该模式并说明原因，而不是猜一个编码器。

## 项目结构

```
src/shared/     纯函数：时间解析、校验、ffmpeg 命令构造、进度解析、吸附显示
                └─ 不依赖 Electron 和 ffmpeg，可直接单测
src/main/       主进程：唯一能 spawn ffmpeg 和读写文件的地方
src/preload/    contextBridge 白名单 API（不暴露通用 invoke）
src/renderer/   React UI
test/           192 个单测 + 固化的 ffprobe fixture
scripts/        验证脚本（见下）
```

`src/shared/` 是设计上的关键：命令构造是纯函数，Dry-run 面板和真实执行走完全相同的代码路径，不会出现「显示的命令和实际跑的命令不一致」。

```bash
npm run commands          # 打印将要执行的 ffmpeg 命令（不需要 ffmpeg）
```

两个端到端脚本（需要 ffmpeg，会真的切视频）：

```bash
node out/tools/verify.mjs <视频>              # 参数比对 + 逐帧哈希 + 取消
node out/tools/verify-idempotent.mjs <视频>   # 吸附幂等性
```

`verify.mjs` 里最有价值的是**逐帧哈希校验**：把源按真实命令语义逐段切出来，逐帧 MD5 与输出比对。参数比对全绿但内容切错位置是可能发生的 —— 开发中正是靠帧哈希发现了 mkv 上切点偏移 2 秒的 bug。

## 踩过的坑

留在这里，因为它们都不是看文档能避开的。

**`-ss` 必须放在 `-i` 之前。** 放在之后（output seeking）配合 `-c copy`，ffmpeg 会从头读并丢弃前面的包，但丢不掉非关键帧对前序帧的依赖，结果是开头一段花屏 —— 这是 `-c copy` 切视频得到黑屏开头的根因。

**`-ss S -t D` 的语义是产出 `[落点(S), S+D]`。** `-t` 相对你请求的 `S` 算，不是相对落点。所以 `-ss` 应该传用户输入的原始起点，让 ffmpeg 自己向前落到关键帧。曾经把已吸附的值又传回 `-ss`，在 mkv 上被再落一格（seek 在关键帧上不幂等），实测切早了 2 秒。

**matroska 的 seek 不幂等。** mkv 以 cluster 为单位 seek，在关键帧后约 0.15 秒内会多退一格（实测 `-ss 6.0` 落到 4.0，而 6.0 本身就是关键帧）。cluster 边界由输入文件决定、无法推算，所以「用实测落点当吸附值」永远不可能幂等 —— 输入任何值它都落得更早，反复回填会一路退到 0。改用 ffprobe 读出的关键帧 pts 列表才与容器无关。

**吸附显示值要向内挪不到 1 毫秒。** 真实关键帧 pts 可能是 `9.5095`（29.97fps 常见），界面只显示 3 位小数。若四舍五入成 `9.509`，用户把这个值输回去时比真关键帧早 0.5ms，只能再退一整个 GOP。起点显示取「严格大于落点的最小毫秒」（`9.510`），终点向下取整，这样回填后吸附结果不变。

**Windows 上 `child.kill()` 杀不掉 ffmpeg。** 必须 `taskkill /pid <pid> /T /F` 杀整棵进程树。

**`-progress` 的 `out_time_ms` 单位其实是微秒。** 这是 ffmpeg 的历史遗留，新版改名 `out_time_us` 但单位相同，解析时两个 key 都要处理。

**concat 用 demuxer 不用 filter。** demuxer 是容器层拼接、支持 `-c copy`；filter 必须解码重编码，与「仅切分拼接」直接矛盾。列表文件里路径要用正斜杠（反斜杠会被当转义符）、单引号要转义成 `'\''`。

**拖拽取真实路径要用 `webUtils.getPathForFile`。** Electron 32 起 `File.path` 已被移除。浏览器 File API 拿不到磁盘路径，这也是选 Electron 而非纯网页方案的核心原因。

## 已知限制

- 输出总时长与「各段时长之和」有毫秒级差异：流复制以 packet 为单位，音频帧（AAC 1024 样本 ≈ 21ms）也无法任意切分
- mkv 上若输入时间落在关键帧后 0.15 秒内，实际会比界面显示的多切一格。方向是向外多切，符合「宁可多切不要缺」的取舍
- 多段拼接处可能有几十毫秒的音画对齐抖动
- 内置预览只能播 Chromium 支持的编码（H.264 / VP9 / AV1）；HEVC、ProRes 会降级为「无法预览」提示，但切分功能不受影响（切分靠 ffmpeg，不靠 Chromium）
- 主要在 macOS 上开发验证；Windows 上的取消（taskkill）和旧版 ffmpeg 的进度解析尚未在真机确认

## 技术栈

Electron + TypeScript + Vite + React，构建用 electron-vite，打包用 electron-builder。不依赖 fluent-ffmpeg（久未维护，抽象反而挡住需要精确控制的参数），不引 UI 组件库。
